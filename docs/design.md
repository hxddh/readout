# Design notes

Readout has one job: make long, frequently rewritten Markdown from AI agents comfortable to read.

## Pipeline

1. **Watch.** An FSEvents stream on the file's parent directory, with file-level events. Agents usually write a temporary file and rename it over the target, which breaks watchers that hold a file descriptor; watching the directory survives that. Changes are debounced (80 ms trailing, at most 400 ms during continuous writes). Half-written files (empty, sharply shrunk within a second of the last write, or ending mid UTF-8 sequence) are retried before rendering.
2. **Parse.** cmark-gfm via swift-markdown, off the main thread. Inline math is protected from Markdown parsing first. Emphasis follows the CJK-friendly amendment (markdown-cjk-friendly): `**注意：**这里` is bold. Where it decides differently from CommonMark (next to CJK characters, CJK punctuation and variation selectors only), the same pass puts an invisible marker beside the `*` or `_` run so cmark decides as the amendment does, and the renderer removes the markers. A line break between two wide CJK characters (not Hangul) renders as nothing, not a space. The document becomes a flat list of blocks: top-level nodes, with every top-level list item as its own block. Rendered HTML per block is cached by exact source and context, so a re-parse only renders blocks that changed.
3. **Fingerprint.** Each block has a fingerprint of its normalized source: trailing whitespace and blank-line runs removed, list markers unified, ordered-list numbers and checkbox state excluded (agents renumber lists and tick boxes; neither is a content change).
4. **Diff.** Myers diff on fingerprints finds unchanged blocks. Between unchanged blocks, deletions and insertions are paired into edits by token-bigram Jaccard similarity (characters for CJK, words otherwise), keeping order. A one-for-one replacement of the same block kind is always treated as an edit, and so is a block whose text is the start of (or almost all contained in) a new block of the same kind, or a paragraph whose text starts a new block of another kind: a block being streamed in that grew, split into several or became a table or code once complete. A short last block (`1.`, `- [ ]`, `|`) whose text is in the new block starting on its line was half written and is not reported removed. If less than 20% of the document survives, it is treated as rewritten; when a count of shared fingerprints shows that, the alignment is not computed at all. Myers' work is bounded: when the differing middle of two long versions is far apart, it is anchored on blocks that occur once in each (patience diff) and the gaps are diffed the same way; a gap of repeated blocks only is aligned by occurrence, greedily or run by run, whichever keeps most.
5. **Identity.** Blocks carry a session-stable slot. Unchanged and edited blocks keep their slot; inserted blocks get a new one. The web view only ever receives insert / replace / remove operations keyed by slot.
6. **Anchor.** Before a patch, the renderer records the first visible block and the offset into it; after applying, it restores that in the same frame. Edited anchor blocks restore proportionally. A ResizeObserver compensates for blocks above the viewport that change height later (diagrams, math, images).
7. **Serve.** The session owns the document: per slot it holds the block's source, its rendered HTML (the render cache's string, not a copy), its kind, and what lays it out unmounted (`BlockLayout`, derived from the HTML when a patch needs it: its length in UTF-16 code units, its line count and its `<tr>` rows, which is what the page's height estimate reads). So the page can ask for the blocks it shows instead of keeping all of them. The page protocol (`PageProtocol`, `PageMessage.blocks`, `BlockReply` in ReadoutCore):
   - **Version.** The page says what it speaks in `ready`: `{type: "ready", protocol: 2, caps: ["lean"]}`. A bare `{type: "ready"}` is protocol 1: every op carries its block's HTML, and none of what follows is used. The app uses a form only with a page that announced it. Quick Look always sends protocol 1 patches.
   - **Lean patches** (`lean`). Each op is the full op without `html`, with `layout: {chars, lines, rows}` in its place (`lines` left out when 1, `rows` when 0), and the patch has `lean: true`. Everything else is as in the full form: `kind`, `cjk`, `anchor`, `src`, `tight`, the marks, deletions and links. An op that has no HTML in the full form (a remove, a replace of a block that renders the same) is the same in both, so an op with neither `html` nor `layout` still means "keep the block as it is".
   - **Request.** `{type: "blocks", version, slots: [...], request}`: the HTML of these slots as of the version the page has applied (the patch's `version`). `request` is the page's id for it, echoed in the reply.
   - **Reply.** `window.readout.blocks({request, version, stale, blocks: [{slot, html}], missing: [...]})`. The session keeps no earlier version, so a reply is always of the current one: `version` is the session's, `stale` is true when the page asked for another, `missing` lists the slots asked for that this version has no block for (removed), and each block asked for comes once, in the order asked. Calls to the page run in order, so a patch the app made before it answered reaches the page before the reply: the page uses a reply only when its `version` is the one it has applied, and otherwise asks again for what it still needs.
   - **Cost.** None of it runs on the update path. The slot index replies use is built when the page first asks in a version, and a lean op's layout is computed when the patch is sent. The native side's memory for a 5 MB document is what it was; serving every block once adds the index. Measured with `perf-probe CORPUS 5000000 heap` (Linux, resident size after `malloc_trim`): a 5 MB document of 32,464 blocks takes 41.7 MB natively before and after this protocol, of which the blocks' HTML is 6.9 MB, shared with the render cache; the index adds 1.1 MB. Rendering HTML on request from source instead would save at most those 6.9 MB, and only with the render cache dropped as well, so it is kept.

## Change marks

Marks are relative to what you have read, not to the previous write. A block counts as read once at least half of it has been visible for 800 ms while the window is focused. The baseline is what you have read: the current version of every read block, the version last read of a block with an unread edit, no unread insertions, and the blocks of unread deletions as last read, where they were; when nothing is unread, that is the current version. Opening the file against it marks exactly what was still unread (the blocks of unread deletions stay removed and take no part in the alignment), so changes read before quitting stay read. It is stored per file (fingerprints, a similarity excerpt capped at 500 characters per block, the whole text of longer blocks, the block's source where it differs from the normalized text, and a flag on blocks of unread deletions) and survives restarts. A record saved before 3.6 (no block sources) is not read: since 4.0 such a file opens as if it were new, once, and its next save replaces the record. Scroll-only position saves never rewrite an unchanged baseline.

An edited block carries a word-level comparison with its text as last read (`WordDiff`): the Markdown source of both versions (list markers, numbers and checkboxes as written, trailing white space left out), tokenized as CJK characters, letter and digit runs, white space and single punctuation, compared with Myers after cutting the shared start and end; long middles are compared line by line first, then word by word inside changed lines. A short unchanged run between two changes is folded into them so a rewritten phrase reads as one deletion and one insertion. Clicking the block's edit mark shows it under the block. Removed blocks show their whole source.

## Rendering

The page is a single WKWebView served from a custom `readout://` scheme. Shiki (JavaScript regex engine) highlights code in a Web Worker (`web/src/hl-worker.js`), never on the page's main thread, and loads and compiles the grammars there too; KaTeX and Mermaid load only when a document needs them. A spare, fully initialised web view is kept warm so a new window renders immediately.

A code block asks the worker for its HTML once it is within four screens of the viewport (so that a reader scrolling fast finds it coloured): on screen first, then by how many screens away, raised as the reader comes nearer, and no longer asked for when it falls out of reach before it arrives. The worker highlights a block a part at a time (parts of about 20 ms, several to a turn of 40 ms, so a more urgent block waits 40 ms at most), sends the lines a block shows on screen first and, for blocks up to 1,000 lines, each part after as it is done; the page puts the HTML in place of the plain `<pre>` once the block is within a screen (sooner would only add elements for WebKit to restyle), all that arrived since the last frame at once in the next one (one layout; what a hold waits for at once), byte for byte what highlighting it on the page gave, keeping the reader's selection in it. A grammar registered while a block is half done (Shiki reloads those that embed it) starts that block again, so the HTML never depends on the order blocks were asked in. What would paint code on screen before it is coloured waits for it instead, for 3 s at most: a document's first paint (the document hidden meanwhile: nothing else of it is on screen yet; the code its first screen may show, by estimated heights, is asked for as its block is made, so the worker highlights it while the page lays the document out, and a window that takes the spare page finds the worker started, Shiki loaded and the spare's grammars compiled), a jump (it scrolls once the lines where it lands are coloured), and find landing in code (highlighting replaces the text it selects). The waiting block goes first, ahead of the rest. A page whose worker cannot start (one could not be made, it failed, or it has not said it is running within 2 s) runs the same highlighter itself, a part a task; Quick Look's log says which one served a preview.

Reader chrome element ids always use the `ro-` prefix (`ro-doc`, `ro-rail`, `ro-notice`, `ro-empty`); document content must never create ids in that namespace. `Slugger` escapes any slug starting with `ro-` to `h-ro-…`, and fragment/link resolution is scoped to the document container so it can never land on chrome.

## Privacy

The page's Content-Security-Policy is the security boundary: it allows no `http:`/`https:` sources at all (`img-src`/`media-src`/`connect-src` cover only `readout:`, `self`, `data:`, `blob:`), so rendering a document can never send a network request no matter what markup it contains. `worker-src 'self'` allows the one worker, the highlighter, from the app's own files (`readout://app/hl-worker.js`) and nothing else: no `blob:` or `data:` worker, no other `readout:` host. A worker does not take the page's policy but the one its script is served with (WebKit lets a worker with none fetch what the page's `connect-src` forbids), so the scheme handler serves `hl-worker.js` with `default-src 'none'; script-src 'self'`: it loads its modules from the app's files and can make no request. It receives code as text and returns HTML; rendering still sends no network request. `HTML.sanitize`/`gateRemoteMedia` is UX only — it turns common remote `<img>`/Markdown images into click-to-load placeholders.

Clicking an image placeholder posts `loadRemote`; the App downloads it with `RemoteFetcher` (ReadoutCore): an ephemeral, cookie-free `URLSession`, 15 s timeout, public hosts only (loopback, link-local, private and unique-local literals, local and single-label names, and non-canonical numeric hosts are refused, and every address a name resolves to must be public; checked before the request and on every redirect — a name that changes its answer between that check and the connection is the accepted residual risk), status, `image/*` and `Content-Length` checked on the headers before any body is accepted, and the 20 MB cap counted while streaming so an oversized body is cancelled as soon as it passes the cap. Bytes are kept in a 100 MB least-recently-used cache and served back over `readout://remote/<token>`. The cache remembers which address each image came from: while its bytes are kept, every page is told (`remoteKnown`) and draws that address from them whenever its block is drawn again, with no click and no request; one click on a placeholder makes the host's other placeholders offer to load them all. Video/audio placeholders open externally instead of proxying. Quick Look never enables remote loading and shows placeholders only.

The one subprocess besides the editor (`xed`): the first open of a Markdown file with no saved reading state that lies in a git repository (a `.git` folder or file at or above it) runs `git show HEAD:./<name>` in the file's folder, so what changed since the last commit is marked against that commit ("Changes since the last commit"). It runs only when `xcode-select -p` names an existing developer folder and `/usr/bin/git` exists (the `/usr/bin/git` shim would otherwise offer to install the command line tools), off the main thread, with a 1.5 s hard timeout and a 5 MB cap on its output; untracked files (git fails), Git LFS pointers, binary content and unchanged files are skipped silently, and files outside a repository never start it. Nothing is written to the repository and nothing leaves the Mac (`GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`; `show` of a committed blob reads the local object store only). The committed version becomes the file's saved baseline like any other read state (`GitBaseline`, `CommitBaseline`).

## Focus and resume

The window subtitle shows the file's status when there is one (deleted, could not be read, decoded as another encoding), else task progress when the document has task lists, and otherwise nothing in a window that shows a tab bar: there the tab's tooltip shows the file's path (`~` for the home folder). A window without a tab bar (System Settings' default "Prefer tabs: In Full Screen" opens documents in windows of their own) has no tab tooltip, so its subtitle shows the file's folder, and two `plan.md` windows differ in the title bar and the Window menu; the subtitle follows when the window joins or leaves tabs. The toolbar holds the sidebar button, a next-change button shown only while something is unread, and the find field; text width is View ▸ Wide Text (`⌥⌘\`). Mark All as Read (⌘K) is undoable (⌘Z, five levels): the document is shown again against the baseline from before, as reopening the window would show it; while the file is momentarily empty (an agent truncating before it writes) Undo waits. A heading's context menu offers Copy Link to Section, which copies a `path#anchor` link to the section. The saved reading position is excerpt-anchored: the first 120 characters of the top block are stored alongside the baseline, so resume survives block-index shifts from agent edits (falling back to the legacy saved index for older records).
